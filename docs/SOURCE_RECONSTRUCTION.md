# Source-shaped reconstruction plan

Status: **proposal only**. Nothing in `src/` has been reorganized under this
plan, and no grouped files exist yet. It records how the 2,360 matched functions
could become source that reads like engine code while staying byte-identical.

The evidence inventories are generated by `tools/analyze_structure.py`:
[`FUNCTION_NAMES.md`](FUNCTION_NAMES.md), [`FUNCTION_GROUPS.md`](FUNCTION_GROUPS.md),
and the practical rules in [`HUMAN_READABLE.md`](HUMAN_READABLE.md). When the local `asm/` index exists, the analyzer also maps named import calls into
matched ranges, resolves exact-start code-related strings, and records them in
`config/function_imports.tsv` and `config/function_strings.tsv`; raw
disassembly, rodata dumps and game assets are never committed.

## Where the source stands

- 2,360 functions, 108,232 bytes, one function per file under `src/`.
- Each file is self-contained: a local `typedef struct { ... } Obj;` with
  `pad` arrays, and the function body.
- There is duplication already: the count/capacity/items vector shape appears
  in several files, eight thunks are the same two instructions, and five
  constant getters differ only in the immediate.
- One file per function is a verification scaffold. It makes a row cheap to
  compile, diff and revert, but it does not look like a translation unit from
  the original program.

## Goal and non-goals

Goal: source with shared object models, behavior names for fields where the
instructions support them, and coherent translation units -- still exactly
matching `Block.elf`.

Non-goals:

- inventing original function names;
- reconstructing all 27,267 starts now;
- producing a playable build;
- mass-rewriting and re-verifying in one step.

## Hard constraints

1. `tools/match.py` compiles the `source` cell of a row and looks up the symbol
   named in the first cell. Several rows may point at one source file, so
   grouping is supported today. **Renaming the symbol breaks the lookup**;
   keep `func_XXXXXXXX` until an alias mechanism exists.
2. Rows with per-row flags (the `-Ospace` startup functions) must not share a
   translation unit with `-O2` rows. Keep them separate.
3. A shared header must preserve exact field widths, signedness and order.
   `s32` versus `u32` changes `cmpw`/`cmplw`; a tighter struct changes every
   later offset.
4. Absolute data addresses are currently emitted as literals (`0x1018953C`,
   `0x1000CF8C`). Replacing one with a named symbol is only safe when
   `config/symbols.txt` resolves it and the relocation encodes the same bits.

## Design

### Layout

Start flat and only add directories after a group is proven:

```
include/
  block.h            shared scalar types
src/
  vector.h            shared Vec model
  vector.c            grouped functions, address order
  thunks.c            identical-body thunks
  constants.c         constant getters
  fn_XXXXXXXX.c       everything not yet grouped
```

The table keeps pointing at whichever file holds the function. A later move to
`src/engine/...` is cosmetic and can wait.

### Type promotion rules

- Build the canonical struct from the union of accesses, keeping every gap as
  an explicit `pad` field.
- Promote a type only when offset, width and signedness agree across all
  functions that would share it. Same offset with a different width is a
  different type.
- Leave the type local when only one function uses it.
- Put the model and prototypes in a header; put bodies in the `.c` in address
  order.
- Use `self` for the first argument, keep the remaining parameter order, and
  do not change linkage or add `static`.
- Name a field `field_XXX` until the instructions justify more. Record the
  evidence in the file comment, not only in the name.
- No bitfields, no packed attributes: explicit pads are what preserve layout.

### Example (illustrative, not applied)

Two files today each carry a private vector type. The proposed shape is:

```c
/* vector.h */
typedef struct {
    s32 count;
    s32 capacity;
    u32 *items;
} Vec;

void func_02020410(Vec *self, u32 value);
void func_02031278(Vec *self, u32 value);
```

```c
/* vector.c */
#include "block.h"
#include "vector.h"

void func_02020410(Vec *self, u32 value) {
    if (self->count >= self->capacity) return;
    self->items[self->count] = value;
    self->count = self->count + 1;
}
```

Both table rows then point at `vector.c`. Verification does not change. The
actual prototypes must come from the target instructions, not from this sketch.

### What "source-esque" should not mean

- No invented function names. `func_02020410` is honest; `vec_append` is a
  guess that also breaks the symbol lookup.
- No plausible-but-unproven symbol substitution for absolute addresses.
- No merging of structs that merely look similar. `020359B4` also has a
  count/capacity/items triple, but at +0x44/+0x48/+0x4C with a different array
  at +0xD0; it is not the `Vec` above.

## Staged plan

0. **Freeze the baseline.** Keep the current table and a matching
   `build/match.log`; the row count and exit status are the reference.
1. **Pilot A -- no-risk grouping.** Move the identical two-instruction thunks
   and the constant getters into one file each, update the table paths, and
   re-run the table. Expected byte result: unchanged. This proves the
   mechanics without touching types.
2. **Pilot B -- one shared model.** Group the genuine vector appends behind a
   header, verify every row, then verify the grouped file as a whole. If a
   function changes, split that function back out and keep the type only if
   its own file still matches.
3. **Offset inventory.** Add `docs/offsets.tsv` (function, offset, width,
   signedness, first evidence) extracted from matched sources. Use it to find
   real overlaps instead of guessing from comments.
4. **Promote only repeated models.** A header is justified at three or more
   functions with identical fields; otherwise the local struct stays.
5. **Repeat per batch; one commit per group.** Full table run after every move.
6. **Re-evaluate per completed subsystem and after each pilot.** Raw match
   count alone is not the trigger. The current 2,360-function table supports
   evidence collection, but mass reorganization is still churn until a group
   passes the full-table check.

## Verification protocol for any reorganization

```sh
python tools/match.py > build/match_before.log   # must exit 0
# move code / share a header / update table paths
python tools/match.py > build/match_after.log    # must exit 0
```

- Compare row names, sizes and the `MATCH` count between the two logs.
- Treat any new `diff`, `BLOCKED` or size change as a failed refactor, even if
  the function still "looks right".
- `build/batch/results.tsv` is a work log, not evidence; only `match.py` is.
- The table is the source of truth for which functions are claimed.

## Risks

- Grouping may change inlining, literal-pool placement or branch relocation
  layout; verify a grouped unit, not just each function in isolation.
- Header field types can silently change compares (`s32`/`u32`) and offsets.
- Per-row flags conflict with grouping.
- Plausible names can hide wrong semantics; keep offset comments and evidence.
- At 2,360 of 27,267 starts (8.65%), premature organization is churn. The plan is
  deliberately deferred.

## Tooling

- `tools/analyze_structure.py` (built): parses all matched bodies plus optional
  named import calls and exact-start code strings, proposes role aliases in
  `config/function_names.tsv`, records evidence in `config/function_imports.tsv`
  and `config/function_strings.tsv`, emits role/clone/regional group candidates
  in `config/function_groups.tsv`, and regenerates the two evidence docs. It
  never edits the table or source.
- `tools/offsets.py` (not built): extract `pad` gaps and field accesses into a
  canonical offset inventory and flag identical models.
- An alias mechanism in `src/functions.tsv` (match symbol versus display name),
  only if readable names ever become worth the extra column. Until then the
  alias TSV is metadata and the verified symbol remains the lookup key.
